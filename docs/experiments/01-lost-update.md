# 실험 01: Lost Update

## 질문
같은 지갑에 입금과 차감이 동시에 들어오면, 잔액이 원장과 어긋나는가?

## 조건
- 지갑 1개, 초기 잔액 1,000,000원 (입금 원장으로 생성)
- 입금 10,000원 × 50건 + 차감 10,000원 × 50건을 동시에 실행 → **정상이라면 잔액은 1,000,000원 그대로**
- 입금·차감 모두 v1 방식: 지갑 SELECT → 엔티티 수정 → 변경 감지 UPDATE
- MySQL 8.4, REPEATABLE READ

## 결과 (1차: 맥북 Testcontainers, 2026-10-27)
환경: `LostUpdateTest`, 스레드 풀 32, HikariCP 기본 풀 10

| 회차 | 성공/실패 | 실제 잔액 | 원장 합계 | 차이 |
|---|---|---|---|---|
| 1 | 100 / 0 | 970,000 | 1,000,000 | −30,000 |
| 2 | 100 / 0 | 890,000 | 1,000,000 | −110,000 |
| 3 | 100 / 0 | 970,000 | 1,000,000 | −30,000 |

- **100건이 모두 성공했고 원장은 전부 남았지만, 지갑 잔액은 매번 틀렸다.** 에러가 하나도 없어서 정합성 검증 쿼리 없이는 알아챌 수 없다.
- 차이는 회차마다 다르다 (덮어쓰기가 몇 번, 어느 쪽으로 겹치느냐에 따라).
- 이번에는 세 번 모두 잔액이 줄었지만, 입금이 덮어써지면 잔액이 줄고 차감이 덮어써지면 늘어난다. 방향은 정해져 있지 않다.

## 원인
```
T1(입금): SELECT balance → 1,000,000
T2(차감): SELECT balance → 1,000,000      ← 락 없는 스냅샷 읽기라 둘 다 같은 값
T1: UPDATE wallet SET balance = 1,010,000 → 커밋
T2: UPDATE wallet SET balance =   990,000 → 커밋   ← T1의 +10,000이 사라짐
```
REPEATABLE READ는 "내가 읽은 값이 트랜잭션 중에 바뀌어 보이지 않게" 해줄 뿐,
다른 트랜잭션이 그 행을 고치는 걸 막지 않는다. JPA 변경 감지는 계산이 끝난 값을 그대로 덮어쓴다.
